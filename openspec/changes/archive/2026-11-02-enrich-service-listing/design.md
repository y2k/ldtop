# Design

## Context

Мотивация описана в `proposal.md`. Проект использует OCaml и dune. В `lib/service_listing.ml` находятся модель `{ label; pid; status }`, строгий разбор `launchctl list`, фильтрация, сортировка, рендеринг и запуск subprocess. `bin/main.ml` вызывает `run` с `/bin/launchctl`. Тесты — небольшие assert-based программы; проверки subprocess сейчас используют `/bin/sh`.

На текущем Mac `launchctl print gui/501/com.openssh.ssh-agent` возвращает `state`, `program`, `arguments`, `path` и `last exit code = (never exited)`. Для незапущенного задания подтверждены `state = not running` и тот же маркер отсутствия завершений. `launchctl managername` возвращает `Aqua`; запрос через `pid/<pid>/<label>` не нашёл службу, видимую через GUI domain, поэтому pid-domain не подходит как универсальное решение.

## Goals / Non-Goals

**Goals:** минимально расширить существующий pipeline, сохранив строгую проверку исходного списка и отделив необязательные подробности. Модель должна различать подтверждённое завершение, отсутствие завершений и отсутствие данных.

**Non-Goals:** мониторинг, метрики процессов, управление службами, новые команды/флаги, сканирование plist-каталогов, чтение логов или вывод environment.

## Decisions

### Подходы и выбранный вариант

Предлагаемый технический выбор: оставить `launchctl list` источником строк и дополнить видимые строки точечными `launchctl print <domain>/<label>`. Альтернативы: разбор полного domain dump усложняет вложенный парсер; чтение plist не даёт runtime-state и достоверной истории завершений. Использовать стандартную библиотеку, без новых зависимостей, кэша и параллельного исполнения.

### Контекст подробностей

Определять контекст один раз после успешного разбора списка и отбора видимых строк. Для root использовать `system`; для обычного пользователя читать `managername` и `manageruid`: `Aqua` соответствует `gui/<uid>`, `Background` — `user/<uid>`, `System` — `system`. Неизвестный manager, некорректный UID или ошибка определения дают неизвестные подробности и одно предупреждение. Не пробовать соседние domains: совпадение Label не доказывает идентичность службы. Эти mappings покрыть fixture-тестами; GUI mapping уже проверен на машине, Background и root требуют проверки при реализации. Другие session-контексты остаются явно неизвестными.

### Модель и разбор

Оставить сырые поля списка, добавить необязательные детали и отдельное значение последнего завершения: числовое, `never`, `unknown`. Парсер подробностей извлекает только непосредственные поля объекта службы и его `arguments` block; одноимённые поля вложенных environment, sockets и coalitions не учитываются. Неизвестные поля игнорируются; непонятный или повреждённый целевой фрагмент не превращается в выдуманные данные.

`State` — состояние launchd, а не вывод из PID. После обратной связи пользователя команды и пути исключены из вывода. Парсер может сохранять эти поля, но отдельный формат их отображения не нужен. Управляющие символы в отображаемых полях экранируются.

`last exit code = (never exited)` даёт `never`; числовое поле даёт число, включая настоящий `0`. Без этих данных ненулевой status исходного списка сохраняется, а нулевой становится `unknown`. Отсутствие поля или `runs = 0` сами по себе не доказывают `never`.

### Получение и ошибки

Сначала полностью разобрать исходный список, затем применить существующий фильтр `com.apple.` и сортировку, затем собирать детали. Для пустого результата дополнительных вызовов не требуется. Передавать команды через argv без shell-интерполяции. Выделить небольшой инъецируемый runner для fixture-тестирования последовательности вызовов, сохранив реальный subprocess-тест.

Начальная ошибка списка остаётся фатальной и не печатает таблицу. Ошибка отдельного `print` даёт краткое предупреждение с Label и оставляет строку; неизвестный контекст даёт одно предупреждение. stdout подробных запросов не пересылается в терминал целиком. Отсутствующие необязательные поля допустимы; повреждённый формат сопровождается предупреждением. PID и состав строк берутся только из исходного snapshot.

### Таблица

Порядок: `Service`, `PID`, `State`, `Exit`. Для `application.*` взять ближайший к executable непустой компонент `.app` из `program`, убрать расширение; если его нет, оставить исходный Label. Для других служб удалить один начальный `com.`, `org.` или `us.`, сохранив остальные префиксы. Не обращаться к файловой системе и не угадывать имя по числовому хвосту.

Ширина колонок определяется данными и заголовком. Имя сокращается слева через `...` до 40 символов, State — справа до 16. Если отображаемые имена совпали, добавить в квадратных скобках кратчайший различающий dot-separated хвост полного Label; хвост не обрезать. PID выравнивается вправо, остальные поля влево, между колонками два пробела. `State` и `Exit` при нехватке данных — `unknown`, отсутствующий PID — `—`. Полные Label остаются ключами сортировки, фильтрации и запросов. Без дополнительных флагов и команд.

## Risks / Trade-offs

- Нестабильный диагностический формат `launchctl print` → узкий парсер, fixtures с вложенными полями и честные placeholders при изменениях формата.
- Несколько subprocess вместо одного → запросы только для видимых строк; проверить время на реальном списке до завершения реализации.
- Служба может измениться между list и print → сохранить исходные строки и PID, не обещать атомарный snapshot всех деталей.
- Нестандартный bootstrap context → не искать Label в других domains; показать неизвестные детали. Проверить mappings для поддержанных контекстов.
- Короткие имена могут совпасть → различать хвостами Label; в редком случае длинного различающего хвоста колонка может превысить 40 символов.
- Изменение текстового формата → явно отметить breaking change; числовой `0` больше не является fallback.

## Migration Plan

Обновить модель, получение данных, рендеринг и тесты в одном изменении. Выполнить `dune runtest`, `dune build` и read-only smoke-test `ldtop ls` через dune с сопоставлением нескольких строк с `launchctl print`. Персистентных данных нет; откат — возврат предыдущей версии программы.
