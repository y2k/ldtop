# Design

## Context

Мотивация — в `proposal.md`. Весь текущий путь списка находится в `lib/service_listing.ml`: `collect` фильтрует строки, один раз определяет domain и запрашивает `print`; `parse_details` сохраняет source path, но не читает файл. `render` строит четыре колонки, тесты проверяют точные строки и последовательности команд. CLI не имеет флагов; библиотека зависит только от `unix`.

Проверены локальные man pages `launchctl` и `launchd.plist`. `blame` описывает ближайшую причину только работающей службы, является диагностическим интерфейсом и не обещает стабильного формата. На реальных пользовательских службах новые источники в рамках планирования не проверялись.

## Goals / Non-Goals

**Goals:** сохранить существующий snapshot-подход и идентичность строк; независимо получать конфигурацию триггеров и причину запуска; явно отличать данные файла от runtime; изолировать ошибки необязательных источников.

**Non-Goals:** история запусков, анализ unified logs, точное определение инициировавшего процесса, проверка истинности условий KeepAlive, вычисление следующего запуска, сканирование plist-каталогов, новая команда подробностей, кэш и параллельные запросы.

## Decisions

### Подходы

Выбран обсуждённый компактный вариант: добавить колонки в `ls`. Отдельная команда подробностей сохраняла бы узкую таблицу и позволяла раскрыть все условия, но требовала бы дополнительных действий пользователя. Автоматический анализ логов для остановленных служб резко расширяет стоимость, права доступа и неоднозначность; вместо этого показываем `unknown`.

Для условий используем связанный plist, для причины — независимый `blame`. Альтернатива — разбирать только runtime `print` — не гарантирует полноту исходных настроек и требует разбирать нестабильные вложенные секции. Не смешиваем два разных источника условий без возможности установить их приоритет; для динамически submitted приложений без plist оставляем `unknown`.

### Источник конфигурации и формат данных

Читать только абсолютный source path из `print` в уже выбранном domain. Submission descriptions уже превращаются в `None`; относительные или неидентифицируемые значения не использовать. Не строить пути из label. Проверять, что корневой объект — dictionary и его `Label` точно совпадает с полным label строки. Файл может измениться после bootstrap: префикс `plist:` обязателен и не сокращается слева.

Системный `/usr/bin/plutil -convert json -o - <absolute-path>` даёт общий путь для XML и binary plist без записи на диск. Запускать через массив аргументов, как существующий `execute`, без shell. Для разбора использовать `Yojson.Basic` и добавить `yojson` в `lib/dune`; минимальные инструкции установки зависимости добавить в проектную документацию при реализации. Самописный XML/JSON-парсер или разбор `plutil -p` сложнее и менее надёжен. Неподдерживаемые JSON-конвертацией plist-типы дают обычный fallback.

### Модель и сбор

Добавить в подробности optional summary триггеров и optional reason; `None` означает `unknown`. Держать разбор JSON и свёртку поддерживаемых настроек чистыми функциями. Потребуется отдельный внедряемый reader plist рядом с существующим launchctl runner, чтобы fixtures не зависели от реальной файловой системы. Не вводить общий framework источников.

После первоначального списка и определения domain для каждой видимой строки:

1. Получить `print` и сохранить всё распознанное по прежним правилам.
2. При наличии допустимого source path получить и проверить plist, затем сформировать summary.
3. Если в первоначальном списке был PID, независимо от результата предыдущих шагов выполнить `blame <domain>/<full-label>`.

Нельзя возвращать строку сразу при ошибке `print`, как сейчас: это пропустило бы независимый `blame`. При неизвестном domain не выполнять ни запросы подробностей, ни `blame`; оставить одно предупреждение о контексте. Нет PID — нет `blame`. PID и состав строк остаются снимком из `list`.

### Сводка условий

Стабильный порядок и обозначения:

| Ключ | Сводка |
| --- | --- |
| RunAtLoad=true | `load` |
| KeepAlive=true | `keepalive` |
| KeepAlive=dict с условиями | `keepalive(cond)` |
| StartInterval=N, N>0 | `every Ns` |
| StartCalendarInterval | `calendar(M H D Mo W)`; отсутствующие поля `*`, несколько расписаний разделяются `;` |
| WatchPaths / QueueDirectories | `watch(N)` / `queue(N)` |
| StartOnMount=true | `mount` |
| MachServices | `mach(N)` включённых объявлений: true или dictionary, false не считать |
| Sockets | `socket(N)` именованных объявлений, не отдельных дескрипторов внутри массива |
| LaunchEvents | `event(N)` дескрипторов внутри event subsystems |

Проверять типы, положительность интервала, допустимые диапазоны календаря (Minute 0–59, Hour 0–23, Day 1–31, Month 1–12, Weekday 0–7). Пустое календарное dictionary содержит только wildcard. Для массивов сохранять порядок; корректные элементы сохранять при некорректных соседях. Проверять структуры коллекций и стандартных условий KeepAlive, не интерпретировать их как факт срабатывания. Не разворачивать содержимое event descriptors или socket options в таблицу.

False и пустые коллекции не добавляют триггер; неизвестные верхнеуровневые ключи игнорируются. При отсутствии распознанных включённых условий использовать `plist:none-known` (не «запускается только вручную»). Ошибка поддерживаемого значения оставляет корректные токены, добавляет `unknown` и одно предупреждение на источник; без корректных токенов — просто `unknown`. Имплицитные следствия KeepAlive не выдаются за явно заданный RunAtLoad.

### Причина и диагностика

При успешном `blame` убрать только внешние пробелы/переводы строк, сохранить непустой текст без классификации по ключевым словам: неизвестная формулировка сама по себе не ошибка. Внутренние управляющие символы экранировать существующим `escape`. Ошибка выполнения или пустой stdout — `unknown` и предупреждение с label и названием источника. Не угадывать причину по `Triggers`, PID, state или Exit.

Обобщить текст ошибок `execute`, сейчас жёстко называющий `launchctl`, чтобы ошибка `plutil` была названа верно. Опциональные процессы остаются quiet, а диагностика проходит через `warn` с экранированием. Обычное отсутствие source path или первоначального PID предупреждения не требует.

### Представление и совместимость

Порядок: `Service PID State Exit Triggers Reason`. Использовать существующее выравнивание с правым PID, учитывать новую последнюю колонку вместо текущего индекса 3. Новые лимиты 32 и 40 символов после экранирования, сокращение справа. Имена по-прежнему сокращаются слева, disambiguation не меняется. Ограничение старого теста на общую длину строки 80 заменить проверками отдельных колонок: новая таблица закономерно шире.

Справка объясняет `plist:`, диагностический характер Reason, отсутствие истории у остановленных служб и то, что условные/множественные настройки показаны кратко. Не добавлять флаги. Показ путей plist и команд по-прежнему запрещён; пути из конфигурации WatchPaths не выводятся, показывается число.

## Risks / Trade-offs

- [Файл отличается от загруженного задания] → явный `plist:` и описание в справке; отсутствие обещания runtime-точности.
- [Формат blame меняется] → сохранять диагностический текст без классификатора, тестировать успешные и пустые ответы; не обещать стабильный словарь причин.
- [Служба перезапускается между запросами] → snapshot не атомарный; Reason относится к службе на момент запроса, не является доказательством причины запуска исходного PID.
- [Дополнительные процессы увеличивают задержку] → максимум один `plutil` на известный source и один `blame` на строку с PID; отсутствующие источники и скрытые строки не опрашивать. Проверить скорость обычного списка при smoke-test.
- [Новая зависимость] → только готовый JSON-парсер `yojson`; проверка доступности и сборки входит в реализацию.
- [Частичная конфигурация и сокращение скрывают детали] → `unknown`, `none-known`, `keepalive(cond)` и `...` выражают ограничение, а не выдуманную точность.

## Migration Plan

Обновить библиотеку, её зависимости, fixtures и CLI help одним изменением. Выполнить тесты, сборку и read-only smoke-test. Миграции данных нет. Откат — возврат реализации и зависимости к четырём колонкам; настройки launchd не затрагиваются. Позиционные потребители текста должны учитывать две новые колонки.
